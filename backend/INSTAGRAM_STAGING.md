# Instagram webhook — safe staging preparation (13 October 2026)

## Deployment scope

This phase creates **only** a separate Instagram callback handler on Sendro's
**dev/staging** code. It does **not** change the WhatsApp routes, Inbox polling,
conversation/message schemas, or the shared PostgreSQL database.

Callback path: `/webhook/instagram`

Intended staging callback URL (when the staging deploy is Live):

`https://sendro-backend-staging.onrender.com/webhook/instagram`

There is also a **production-shared database** behind this staging backend.
Do not use this feature to save Instagram data until we have a reviewed
multichannel schema and an explicit shared-DB migration approval.

## Environment variables (configure on the *staging backend* only)

- `INSTAGRAM_WEBHOOK_VERIFY_TOKEN`: new random secret string generated by the operator.
  Enter the **same value** in Meta's "Verify token" field. It is a secret
  used to confirm Meta's initial verification GET; it is **not** an Instagram
  access token or the WhatsApp webhook verify token.
- `INSTAGRAM_APP_SECRET`: the **Instagram app secret** shown under the
  "Instagram API with Instagram Login" use case, required to check POST
  request signatures. Never paste it into GitHub, logs, or chat.
- Instagram API access tokens will require separate secure handling once
  the messaging pipeline is implemented. They are **not** used in this phase.

## Safety behavior

- GET challenge: returns Meta's exact text/plain `hub.challenge` only when
  `hub.mode=subscribe` and its `hub.verify_token` matches the configured
  `INSTAGRAM_WEBHOOK_VERIFY_TOKEN`. Missing configuration returns 503;
  wrong tokens return 403.
- POST event: validates `X-Hub-Signature-256` using the Instagram App Secret
  and always returns **503** after verification. Incoming notifications are
  **not stored or acknowledged**, because ingestion is not built yet.
  An unsigned/incorrectly signed event returns 403.
- Deliberately do **not** switch the Instagram Webhook Subscription ON,
  and do **not** publish the Meta App to receive real customer DMs yet.
  Publishing may affect the preexisting WhatsApp app's approval/audience.

## Follow-on implementation before enabling

1. Confirm Meta App status and permissions for **Instagram Login**.
   App publication is separate from App Review / Advanced Access.
2. Plan and approve multi-channel / eventually multi-tenant message isolation,
   including Instagram business account ID + Instagram scoped sender ID and
   webhook message id, without breaking existing WhatsApp phone-based records.
3. Build reliable signed POST ingestion with deduplication, safe retries,
   database persistence and status notifications, plus outbound Instagram send
   handling respecting Meta policies. Add local integration tests.
4. Add channel-specific Inbox filter/badges, assignment and access boundaries.
5. Configure Instagram credentials and callback separately in Render staging;
   test webhook handshake before turning on any delivery. Test end-to-end
   only after persistence is working and Meta publication is deliberately approved.
6. Request Meta App Review for the production audience as required.
   Verify test messages from app-role accounts separately from unrestricted
   customer traffic.

## Zero-impact checklist

- No WhatsApp webhook path, Meta sender settings or polling frequencies changed.
- No secrets stored in repository or logged by this module.
- No PostgreSQL table change, data migration or conversation write.
- No Instagram webhook POST ever returns 200 until we have reliable persistence.
